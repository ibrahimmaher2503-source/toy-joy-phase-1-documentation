# Testing 07 — Agent Test Protocol

**Parent:** `docs/14-test-plan.md`
**Audience:** any AI agent (Claude Code, Codex CLI, or similar) working on this repository.
**Purpose:** define what the agent must run, what it must report, and what it may never claim.

**Copy the "Agent Rules" section of this document into `AGENTS.md` / `CLAUDE.md`.** A protocol the agent does not read is not a protocol.

---

## Why This Document Exists

An agent working on a large codebase has a structural incentive to report success: the task looks finished, the code looks right, and running a long test suite is slow. The failure mode is not dishonesty in any dramatic sense — it is the quiet substitution of *"I believe this is correct"* for *"this was verified"*.

In a system that posts stock movements and customer payments, that substitution is expensive. This document removes the ambiguity by making completion a mechanical fact — an exit code and a report file — rather than a judgment.

---

## Agent Rules

### Rule 1 — Completion is defined by the orchestrator, not by the agent

A task, milestone, or release is complete only when `scripts/run-tests.sh` has been run at the appropriate level in the current session and exited zero.

The agent may not declare a task done based on reading the code, reasoning about correctness, or confidence in the implementation. Those are inputs to writing the code, not evidence about the code.

### Rule 2 — Never claim a test result that was not produced this session

The agent must not write "all tests pass", "tests completed", "verified", or any equivalent unless it is quoting counts from a report file generated by a run it performed in this session.

If the agent did not run the suite, it says so plainly: *"I have not run the test suite; the task is not verified."* That sentence is always available and is always the correct thing to say when it is true.

If a run failed and the agent has not yet fixed the cause, it reports the failure. A failing test is information, not a problem to be managed away.

### Rule 3 — Which level to run

| Situation | Command |
|---|---|
| An implementation task is believed complete | `bash scripts/run-tests.sh task` |
| All tasks in a milestone are task-level green | `bash scripts/run-tests.sh milestone` |
| A release candidate is proposed | `bash scripts/run-tests.sh preprod` |
| The change touches numbering, stock posting, wallets, loyalty, gift cards, price approval, shift close, permission resolution, or offline sync | escalate to `milestone` regardless of task size |

### Rule 4 — On failure, fix the cause

If `FAIL > 0`:

1. Read the failure log in the report.
2. Fix the underlying defect.
3. Re-run the same level.
4. Repeat until zero.

**Never:** edit the report file, delete or skip the failing test, weaken an assertion, add a conditional that makes the test pass in the test environment, or mark the test as expected-to-fail. If a test is genuinely wrong, fix the test and say explicitly that the test was changed and why — a changed test is a claim that needs review, not a silent cleanup.

### Rule 5 — On skip, escalate to the human

If `SKIPPED > 0`, a tool is not installed and that check did not run. The agent must name the missing tool and ask the human to install it.

**Never:** treat a skip as a pass, remove the check from the orchestrator to clear the skip count, or describe the run as clean when checks were skipped. At milestone level, `SKIPPED > 0` is a blocking finding.

### Rule 6 — Never fill in a human checklist

The manual checks in `docs/testing/05-manual-checklists.md` — manual visual review, UAT, physical device test, disaster recovery, security review, migration rehearsal, browser matrix, go/no-go — require a named human and a date.

The agent must never check those boxes, write a name into them, write "verified" or "N/A" or "completed by agent", or describe them as satisfied. It may prepare the checklist, run everything automatable around it, and point out which items are outstanding.

If the agent notices itself reasoning toward *"this one is obviously fine, I can mark it"* — that is precisely the case the rule exists for. Leave it blank.

### Rule 7 — Report format

Every time the agent runs tests, it reports in this shape:

```
Test level: <task|milestone|preprod>
✅ Passed: N   ❌ Failed: N   ⏭️ Skipped: N
Report: docs/testing/reports/<filename>.md

[If FAIL > 0: what failed, the cause, what was changed, re-run result]
[If SKIP > 0: which tool is missing and what the human needs to install]
[Manual checks outstanding: <list>]
```

The counts are copied from the report, not summarised or rounded.

### Rule 8 — Write the tests, do not only run them

When implementing a task, the agent writes the tests required by the traceability matrix for that requirement's tier, including the mandatory negative cases from `docs/testing/03-test-catalog.md`.

A task implemented without its required negative tests is incomplete even if the orchestrator passes — the orchestrator can only run tests that exist. The agent must state which test cases it wrote and which required cases remain unwritten.

### Rule 9 — Update the traceability matrix honestly

When a requirement's tests are complete, update its status in `docs/testing/02-traceability-matrix.md`.

`☑` means every required test type has a passing test that would fail if the behaviour regressed. `◐` means partial. Marking `☑` optimistically is worse than leaving it `☐`, because it removes the requirement from everyone's attention.

### Rule 10 — Raise ambiguity, do not resolve it

If an acceptance criterion is ambiguous — a limit that is not specified, a permission that is not defined, a state transition that is not described — the agent records it in the Gap Register in the traceability matrix and asks.

It does not invent the missing rule and test against its own invention. A test that asserts a guessed rule is worse than no test: it makes the guess look approved.

## What the Agent Prepares vs What the Human Decides

| Activity | Agent | Human |
|---|---|---|
| Write automated tests | ✅ | reviews |
| Run the orchestrator | ✅ | — |
| Fix failing tests by fixing the code | ✅ | — |
| Report results | ✅ | reads |
| Update traceability status | ✅ | verifies |
| Prepare manual checklists | ✅ | — |
| Sign manual visual review | ❌ | ✅ |
| Accept UAT | ❌ | ✅ |
| Test physical devices | ❌ | ✅ |
| Run the DR exercise | ❌ | ✅ |
| Perform the security review | ❌ | ✅ |
| Approve production go-live | ❌ | ✅ |

## Hooks (Recommended)

Rules that depend on the agent remembering them will hold most of the time. Rules enforced by tooling hold every time.

Configure a `Stop` or `PostToolUse` hook so that the task-level suite runs automatically after code changes, and the agent cannot end a turn claiming completion without a real result. This is the difference between a protocol and a preference.

```
Hook: on stop, if source files changed this session,
run: bash scripts/run-tests.sh task
```

The hook does not replace these rules — an agent should follow them because they produce correct work, not because it is being watched. But the hook covers the case where the agent's context has grown long and the protocol has drifted out of attention, which is a real failure mode and not a hypothetical one.

## Verification Questions for the Human

If you want to check whether the protocol is actually being followed, these three questions surface most drift:

1. **"Show me the report file for that run."** A report that does not exist means the run did not happen.
2. **"Which negative test cases did you write for this task?"** Positive-only coverage is the most common quiet gap.
3. **"What is still unchecked in the manual checklist?"** An agent that answers "nothing" is either wrong or has filled in boxes it must not fill.
